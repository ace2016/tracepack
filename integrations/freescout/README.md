# Tracepack for FreeScout

**Unofficial, community-built integration. Not affiliated with, reviewed by, or endorsed by
FreeScout.** Say so anywhere this module is described or distributed, unless FreeScout formally
endorses it in the future.

A [FreeScout](https://freescout.net) module that adds a "Send to Tracepack for FreeScout" button
to each conversation. Clicking it builds a `tracepack-evidence` v1 payload from that
conversation's thread and attachments, then hands it to the customer's own Tracepack tab via the
same `window.open` + `postMessage` handshake documented in
[`EMBED_GUIDE.md`](../../packages/evidence-interchange/EMBED_GUIDE.md) and demonstrated in
[`examples/embed/gift-shop-refund-button/`](../../examples/embed/gift-shop-refund-button/). Nothing
here talks to a Tracepack server, and no account is required on either side.

The payload is assembled server-side in PHP (`Support/EvidencePayloadBuilder.php`), per the
embed guide's own recommendation to build the payload from a trusted backend rather than from
code running in a browser a customer could tamper with. The agent's browser only ever receives
the finished, already-hashed JSON and forwards it.

## The actual flow

```
FreeScout conversation
  -> agent clicks "Send to Tracepack for FreeScout"
  -> controller builds a tracepack-evidence v1 payload from the WHOLE conversation
     (every thread message, every supported attachment; nothing is selected or filtered)
  -> browser opens Tracepack's external-import screen and posts the payload to it
  -> Tracepack shows a plain list of the customer's existing packs to choose from,
     plus a "start a new pack with this evidence" option
  -> customer confirms; Tracepack creates one summary note for the conversation
     plus one item per attachment, all tagged with provenance
```

Two things worth being precise about, since it's easy to assume more automation exists than
does:

- **No content selection.** The whole conversation goes into the payload every time. There is
  no step where an agent picks which messages or attachments to include. If that matters, it
  would need to be built, it is not here yet.
- **No pack recommendation.** The review screen on Tracepack's side lists every existing pack
  in a plain dropdown; nothing ranks or suggests one based on the ticket's subject, customer
  email, or order number. The customer picks manually, or starts a new pack. Building an actual
  recommendation (matching ticket content against existing packs) is a real feature, not yet
  attempted, and would need its own design pass rather than being assumed to already work.

## FreeScout's statements stay observations, never findings

The conversation thread becomes `observations` on the imported evidence, not Tracepack's own
`privacyFindings`. These are two structurally separate fields on every evidence item (see
`packages/evidence-core/src/index.ts`'s `EvidenceItem` type, and `SPEC.md` section 4 in
`packages/evidence-interchange`), never merged, never rendered as if they were the same kind of
claim. `privacyFindings` is only ever written by Tracepack's own PII scanner, run fresh on
import; nothing from FreeScout's payload can populate it directly. The synthesized summary note
that carries the conversation text also opens with a fixed banner making this explicit
("GENERATED BY TRACEPACK... a rendering of claims reported by an external producer... not
independently verified"), so the distinction holds both in the data model and in what a reader
actually sees.

## What's actually verified

`Support/EvidencePayloadBuilder.php` is a plain PHP class with no Laravel or FreeScout
dependency, so it can be exercised on its own:

```
php Modules/TracepackForFreescout/Support/test-payload-builder.php
```

This builds a payload from a fake conversation (two thread messages, one PDF attachment, one
unsupported `.docx` that should be described in an observation rather than silently dropped),
checks the attachment's `content_hash` and the exclusion behaviour, and writes the result to
`tests/fixture-payload.json`.

```
cd tests && node verify-payload.mjs
```

This cross-checks that fixture against the **real** `@tracepack/evidence-sdk`, the same package
the Tracepack app itself uses to validate and import incoming evidence. It confirms both that
the payload is schema-valid and that the PHP-computed `payload_hash` matches the TypeScript
RFC 8785 implementation byte for byte. (This caught a real bug during development: PHP's
`json_encode` escapes forward slashes by default, which silently produced a different canonical
string, and therefore a different hash, than the JS side for any payload containing a URL. Fixed
with `JSON_UNESCAPED_SLASHES`.)

That's the part of this module that's genuinely proven correct: the interchange contract
implementation. What's **not** verified is the FreeScout integration surface. The controller,
routes, service provider, and blade view were written against FreeScout's publicly documented
model and module API, not confirmed against a live install. Before using this for real:

- Confirm `App\Conversation`, `App\Attachment`, and the `Thread` relation's field/method names
  (`created_by_customer`, `createdByUser`, `getContent()`, `body`, `customer_email`, `url()`)
  against your installed FreeScout version, since these can and do change between releases.
- Confirm the Eventy hook name in `TracepackForFreescoutServiceProvider::boot()`
  (`conversation.append_action_buttons`). It follows the naming pattern FreeScout's other
  module hooks use, but has not been confirmed against a running instance. If the button
  doesn't appear on a conversation after installing, this is the first thing to check: search
  your FreeScout version's `resources/views/conversations/` partials for the actual
  `Eventy::addFilter`/`addAction` calls already firing there. The route itself
  (`GET conversations/conversation/{id}/send-to-tracepack-payload`) works regardless of whether
  the hook fires, so linking to it manually is a working fallback while you confirm the hook.

## Installing

1. Copy `Modules/TracepackForFreescout/` into your FreeScout installation's `Modules/`
   directory.
2. From the FreeScout root: `php artisan module:enable TracepackForFreescout` (or enable it
   from Manage → Modules in the admin UI, if your version lists locally-placed modules there).
3. Optionally set `TRACEPACK_APP_URL`, `TRACEPACK_PRODUCER_ID`, and `TRACEPACK_PRODUCER_NAME`
   in your FreeScout `.env`, see `Modules/TracepackForFreescout/Config/config.php` for defaults.

## What it does not do

- No shared or hosted pack, no email delivery, no copy saved on FreeScout's own servers, the
  same scope limits as the embed guide describes. The evidence moves directly from the agent's
  browser tab to the customer's.
- Only `application/pdf`, `image/jpeg`, `image/png`, and `image/webp` attachments are included
  as evidence files, matching the v1 schema. Anything else attached to the conversation is
  named in a text observation instead of included as a file, so it's still visible to the
  customer, just not as an attachment they can preview or export as its own document.
- PII in the conversation thread text is not scanned or redacted by this module. Tracepack's
  own privacy scanner runs on the customer's side once the evidence lands in their pack, the
  same as it does for a manually typed note.
- No content selection and no pack recommendation, see "The actual flow" above.
