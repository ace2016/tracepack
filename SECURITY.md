# Security

## Trust model (read this first)

Tracepack is local-first: your projects and evidence files live in your browser's IndexedDB
storage. Nothing is uploaded anywhere by default: there is currently no server, no account,
and no cloud sync.

### What integrity hashes prove, and what they don't

Every piece of evidence gets a SHA-256 `contentHash`. Attachments coming through the
`tracepack-evidence` interchange contract get two separate hashes:

- **Attachment integrity** (`content_hash`): SHA-256 of the original binary bytes. Proves the
  bytes weren't altered relative to what was hashed.
- **Payload consistency** (`integrity.payload_hash`): SHA-256 of the RFC 8785 canonical form of
  the structured claims. Proves the structured data (observations, timestamps, metadata) wasn't
  altered relative to what was hashed.

**Neither proves who sent the data, or that any claim inside it is true.** See
`packages/evidence-interchange/SPEC.md` §5 and §13 for the full reasoning.

### Producer identity is self-asserted in v1

A payload's `source.producer_id` and `source.producer_name` are declared by the producer, not
cryptographically authenticated by Tracepack. Nothing currently stops a different producer from
claiming the same `producer_id`. Tracepack's UI and exports are written to never imply otherwise:
look for "self-asserted" and "not cryptographically verified" language anywhere producer
identity is shown. If you find a place where this isn't true (a verification badge shown
without actual verification behind it, or wording that overstates what a hash proves), that's a
real bug and should be reported (see below).

### A note on synthesized evidence

When an interchange payload has no attachments, Tracepack synthesizes a deterministic
`text/plain` rendering of the producer's claims to satisfy the one-evidence-item-one-file model.
That rendering is generated by Tracepack, not supplied by the producer; it says so explicitly
in its own text ("GENERATED BY TRACEPACK... not an original document"). Its hash proves the
rendering is intact, never that an original external document existed.

## Researched, not implemented: future authenticated identity

Producer identity authentication is deliberately out of scope for v1. If it's added later, the
research direction under consideration is [Sigstore](https://www.sigstore.dev/), specifically
**Fulcio** (issues short-lived certificates bound to an OIDC identity, e.g. a GitHub or Google
login, instead of a long-lived keypair a producer has to manage) and **Rekor** (a public
transparency log of signing events), tied together by `cosign`-style tooling. This is the same
approach Locktivity's [`evidence-pack`](https://github.com/locktivity/evidence-pack) project
uses for its own attestation layer: a useful reference point, not a dependency Tracepack has
adopted. No home-grown signing cryptography will be built for this; if authenticated identity
ships, it will be on top of established infrastructure like Sigstore, not a bespoke scheme.

## Scope

In scope: the packages and apps in this repository (`apps/`, `packages/`, `examples/`).

Out of scope: issues that require physical access to an already-unlocked device, or that rely
on a compromised browser/OS. Tracepack's local-first model assumes the browser environment
itself is trusted, the same way any browser-based application does.
